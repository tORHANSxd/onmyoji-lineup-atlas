# 御魂计算口径（exact-3）

本版本从平安志 `mumu-snapshot-v1` 库存中寻找六个不同位置的御魂，按阵容码目标检验。计算只生成建议，不操作游戏内穿戴、兑换或强化。

## 依据与单位

静态规则依据用户提供的 `onmyoji_netease_116_2.8.84_py3_small.apk`，只读取指定资源、数据常量和字节码，不运行提取的游戏代码。资源与原APK中同名文件逐个比较SHA-256，哈希保存在 [apk-mechanics.json](../data/apk-mechanics.json) 的 `source.verifiedFiles`。

核对位置包括：`module/ta/TACalcMgr` 的计算与最高值传递、`TACalcHelper` 的式神技能选择、`module/equip/auto_yuhun_helpers.py` 的 `CalcConfig.set_yuhun_suit`、`set_yuhun_suit_attrs`、`convert_equip_suit`、`set_result_attrs`，以及 `AttrCalc.py` 的成长与御魂属性合成。素材名称与觉醒加成来自 cdata `hero`（索引22953），套装属性来自 `equip_suit`（索引26529）。本仓库仅保留必要数据事实与本工具实现，不分发APK或提取的游戏代码。

2026-09-19 补充核对 `YuhunMatchLogic`（6977）、`YuhunAlgo`（7126）、`YuhunAlgoGen`（7124）及 `auto_yuhun_criteria_expression`（33249）。原资源哈希重新核验通过，字段与证据哈希见 [soul-objectives.json](../data/soul-objectives.json)。游戏会委托 `g37misc.auto_yuhun_calc_top_n` 或 `auto_yuhun_generate_algo` 执行原生搜索，生成算法还含种群、迭代次数及候选数量配置；本工具没有执行或完整复刻该原生内核，不能宣称逐项复现游戏的最终返回顺序。

- 平安志 `attrs` 前六项依次为生命、速度、暴击伤害增量、暴击、防御、攻击；每项四元组的第一个值是基础值，其余可能含旧穿戴，不能再当作基础叠加。暴击伤害基础增量0.5对应总倍率1.5。
- 命中、抵抗基础值及觉醒固有加成来自静态角色规则。攻击、生命、防御按 `基础 × (1 + 百分比加成) + 固定加成`；觉醒比例与御魂比例相加。其他面板加和。
- 阵容码 `critical_rate`、`critical_pow`、`debuff_acc`、`debuff_res` 上下限使用百分数；库存与内部计算使用小数比例。显示时再转换成百分数，不提前截断内部精度。
- `ExtraAttr.attackRate` 作用于合成后的攻击，然后加 `ExtraAttr.attack`；额外暴击与暴伤直接相加。其他不认识的额外属性保持待核对。
- 普通同套2/4/6件分别产生1/1/2次二件属性。防御二件套为30%；无刀取为20%暴击伤害。首领固定属性已经在平安志副属性中，不能再凭套装名称重复加一次。

## 阵容条件

支持指定式神、觉醒状态、技能最低等级、御魂星级与强化等级范围、套装2/4/6件数量、六个位置的主属性、八项面板上下限、原码额外属性及最高属性次序。原码等级/星级是计算推荐，按库存实际实例计算并提示差异；手工配置仍可设最低等级/星级要求和精确技能等级。

套装条件同时满足。4+2中，指定四件套本身已提供的二件加成，不能冒充额外要求的二件套；重复同套数量合并，六件同套只能贡献两次普通二件加成。`two_suit` 中重复属性也保留次数。

原码标记某成员「最高属性」后，后续计算成员的该属性上限取前者实际穿戴值（不加其原码额外属性），减0.1；比例属性减0.001，即0.1个百分点。检查遵守原码槽位次序，不把它改为全队无方向的大小比较。全队方案同时检查式神实例与御魂实例不重复。

计算指标1–12参与候选排序；有明确目标分数的手工配置同时检查阈值。指标是面板函数，不模拟伤害、被动或四件套战斗触发。原码 `use_score` 保留可查，本工具按目标指标与条件缺口选装，不复刻游戏御魂评分的展示排序。

游戏的专用指标覆盖通用公式，候选排序、上界、目标阈值及最终方案都使用同一公式。以下暴伤均为总倍率（例如 1.5），命中、抵抗为小数比例：

| 式神 | 目标 | 游戏公式 |
| --- | --- | --- |
| 云外镜 | 伤害输出 | `(攻击 + 防御 × 2) × 暴伤` |
| 云外镜 | 防御输出 | `(防御 + 攻击 × 0.1) × 暴伤` |
| 久次良 | 伤害输出 | `攻击 × 暴伤²` |
| 季 | 伤害输出 | `攻击 × (暴伤 − 0.5)` |
| 孔雀明王 | 伤害输出 | `(攻击 + 基础攻击 × (0.75 + 效果命中)) × 暴伤` |
| 妙主九命猫 | 伤害输出 | `攻击 × (暴伤 + 效果抵抗)` |

孔雀明王采用 `AlgoMgr.init_algo` 中按当前培养实例基础攻击构造的动态覆盖，不采用表中被覆盖的旧表达式。详情的「高级要求与原码字段」可查看实际公式。

阴阳师／英杰、契灵与术印不参与要求检查，只在详情中展示原码配置；不会造成待核对状态、差距标签或排序扣分。式神 AI 技能设置、协战、保留当前穿戴与库存占用范围不能由缺失的导出信息推断，仍保留相应待核对项。原码说明、操作与替代条件继续在详情中展示。

## 搜索、差距与建议

界面用三个可同时出现的标签：红色「式神缺少」、青灰色「御魂不达标」、橙色「式神技能或等级或觉醒不达标」。缺少按实际实例数量计算；库存有对应式神但不能满足培养条件时计入培养侧，星级也在此列，不与缺少重复计数。原码的推荐等级／星级仍按推荐处理，不擅自提升为硬性要求。内部继续分别记录式神和御魂两侧可行性。

先对全队实际式神实例做匹配，再运行原有完整配装搜索。式神不足时，在计算副本中补上原码培养目标对应的假设实例，以同一套全队约束检查现有御魂是否足够；不写入账号、不改变真实可用方案。属性必须来自相同培养状态的已核验导出或本地官方 40 级六星面板，不外推缺失成长值。找到可行方案即可证明御魂侧可满足；只有穷尽才能判定不足。假设条件和配装在详情中单独标明。

式神／御魂来源条件不完整、协战、未知基础属性、不完整／增量库存等情形进入「待解析 / 待核对」；尚未得出缺口结论时进入「待计算 / 计算中」。不能把一个诊断候选不达标当作整个仓库不足。阴阳师、契灵与术印属于展示范围，不参与可行性结论。

每个阵容独立使用完整库存，同一阵容中式神和御魂实例不重复占用。先将已核验的原码条件作为硬约束，再按原码成员顺序的指标向量作字典序最大化。不是把不同成员的分数加权成一个随意权重。

精确求解采用可暂停生成器与分支定界：全部合格实例留在问题中；对剩余位置使用保守属性区间、套装可达件数、指标上界和最高属性约束剪枝。完全等效的御魂与式神只去除交换实例 ID 的对称排列，保留每份库存的数量。基础属性、技能或任何受支持条件不同的实例不合并。

保留剩余成员逐位置的实例匹配检查，以及两件套的保守可达性检查。最后一位成员的相同精确属性和套装计数前缀可复用搜索结果；该缓存最多保留 2048 个状态，缓存装满后继续正常搜索，不截断候选。候选排序复用，进度消息限频，避免重复传输大快照。

未知属性只在其御魂仍可能满足当前星级、强化和主属性筛选时阻止证明。明确不参与配装的御魂不会把结论变成「待核对」；无法识别的主属性则保留为潜在候选，不能假装排除。超过面板上限与低于下限都不达标，完整排除全部组合后标记「御魂不达标」，不以「待核对」掩盖已确认无解。

没有候选数量、时间或节点预算作为结束依据。仅完整排除其余可能性才给出「式神御魂最优已证」或「原码约束无解」。中间可行解标记计算中，暂停保留本次进程内的完整搜索栈；退出应用后重新搜索。复杂多成员问题可能计算较久，运行时间没有固定上限。

同批 Worker 任务共享完整库存的位置索引与等效实例键，直接调用默认使用新的准备上下文，避免跨库存污染。准备阶段先报告状态，再分段让出执行权。任务采用轮转调度，一个长搜索不会挡住其后的阵容；暂停保留每个任务的搜索栈。

无评分目标，或满足严格恒定条件的线性目标，可在找到完整可行解后直接证明最优。判断同时比较相关基础值、觉醒固有加成、御魂属性和套装效果；不将“当前候选同分”当作全部候选恒定。其他情形继续完整搜索。

解释性诊断在库存超过 192 件时按位置与套装取有界样本，最多查看前三个式神实例，避免初始化长时间阻塞。这个限制只用于解释性候选；精确搜索仍使用全部合格御魂与所有式神实例。样本找不到配装不能证明全库无解。子集诊断不复用全库缓存，预设中任何不在当前候选库存内的御魂都不能进入该诊断方案。

快速有限搜索只生成解释性诊断候选，不参与最优性证明；诊断候选不一定是全库最接近方案。无解表示参与计算的原码式神／御魂约束不能同时满足，某个诊断候选的缺口不代表唯一补法。不完整导出、合并旧库存、未知套装／属性／范围、缺基础值或穿戴归属时，显示所缺资料，不冒称无解。

差距分是解释性排序：缺角色100；技能每级差8；觉醒差15；缺套装每件6；缺位置12；主属性不符8；面板缺口按相对目标差距加权。待核对内容另列，不当作已满足，也不计成通关概率。最接近的方案仅指本轮已搜索候选。

建议先使用已有合格库存，再考虑现有兑换资源，最后刷取或承担随机强化风险。主属性/星级不符、套装缺件、面板超过上限时，不先花资源强化当前错误胚子。兑换建议结合当前库存缺位，提示具体套装和位置；上限超标时建议换低对应属性，避免越强化越偏离。副属性强化随机，不承诺兑换一件或强化一次就一定达标；更新库存后应重新核对。

数值运算使用 JavaScript Number，分支上界含浮点误差余量；叶子复核与常规计算使用同一面板模型。测试以独立全组合穷举验证小实例，并验证重复占用、边界、最高属性和暂停恢复。实际库存基准仅说明特定案例性能，不保证所有五成员问题具有相同耗时。

## 选择、目标与缺口统计

账号载入、库存导入、解析完成和资料更新仅刷新式神缺口，不自动精算御魂。用户可精算全部阵容或勾选项；全选、反选覆盖当前筛选的全部分页，改变筛选或账号即清空临时勾选。目标阵容按库存账号保存在 `targetLineups`，重导同一账号库存保留目标，随备份恢复，删除阵容同步清理目标引用。

打开缺口统计即精算打开时筛选的阵容，复用当前库存已经完成的结果，显示进度并允许暂停、继续。后续结果不会扩大此次统计范围，切换账号丢弃旧计算。计数为受影响阵容数，同一阵容同一种缺口只记一次；展开可查看所涉阵容。

御魂套装排行只统计能证明的位置或同队数量缺口，未知套装作为潜在候选保留。仅证明数值、套装组合或共享占用无法同时满足、却无法归因到某一种套装时，列为「数值或组合不达标」；诊断候选缺件不直接当成整个库存缺件。

## 0.8.0 性能观测

使用 `node tools/benchmark-exact.cjs --synthetic`，在相同 VM 加载器中对照本轮开始前的 HEAD 与当前实现。一次观测中，36 件御魂的无目标和恒定速度场景均从 55,987 个节点降至 7 个，目标向量一致。96,000 件御魂初始化到开始搜索约从 6,087 ms 降至 340 ms；当前首次让出执行权约 0.1 ms，初始化阶段最长一次 `next()` 约 109 ms。完整原始记录与基线提交见 [观测 JSON](../verification/optimization-performance.json)。

这是特定合成样本的单次观测，耗时受硬件、运行环境和同时运行的任务影响。初始化更快不等于所有多成员搜索都能快速完成；产品求解没有增加时间截断。

## 0.9.0 增强关系

阵容可保存任意两位成员之间的属性比较，形式为 A 属性 op (B 属性 × 倍率 ＋ 差值)。八类面板属性均可比较，百分比使用百分点；仅比较穿戴后的原始面板，不使用原码额外战斗加成。关系在成员组合搜索时作为约束，不截断候选；顺序变化使用稳定成员标识重新映射位置。游戏 V3 不包含此字段，所以仅随御契资料/备份保存，导出时必须确认损失提示。
