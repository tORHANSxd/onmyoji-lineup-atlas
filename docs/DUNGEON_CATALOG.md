# 全客户端副本资料

御契桌面版在「阵容库 → 全客户端副本与规则」按需读取本地资料。打包前将生成的目录放在 `data/dungeon-catalog`，即可随桌面版打开。运行时也可以在这个面板选择已有的副本资料目录。

「按关卡查找」从同版的资料表列出 31,221 条关卡、战斗模式及玩法参数配置，包括通用 PvE、御魂、觉醒、秘闻、探索、地域鬼王、契灵、六道之门、阴阳寮和历次活动。可按名称、玩法及关卡或编组 ID 搜索。关卡详情连到编组、场景、活动时间、首领及规则文本，点击敌人可核对属性、免疫与该等级的技能说明。原始字段及来源 SHA-256 可展开查看，也可跳转到原表或关联关卡。

派生索引和原表分别校验。本版有 92,303 条可解析引用。另有 14 个通用 PvE 关卡指向缺失的敌方编组，ID 为 18 至 26、11111、11112、20110、20719 和 20831，均未出现在 2.8.87 基础 APK 或 `0.0.816` 资源的 `BattleMonstersInfo`。详情保留原编号和缺失提示。索引包含历史、副本变体和内部配置，区服实际开放仍以游戏内状态为准。「查资料表」可继续检索全部原表。旧目录没有派生索引时，面板直接打开资料表。

《阴阳师》2.8.87 的 `0.0.816` 资源包中，已从 3,851 个客户端配置模块读取 3,847 张表，共 659,646 条记录。另有两张由战斗脚本提取的注册表，包含 934 条记录。主要资料包括 17,617 条通用 PvE 关卡、17,563 条战斗编组、491 条场景站位、217 条通用战斗模式以及御魂、觉醒、秘闻、阴阳寮狭间暗域、活动组队等玩法专表。表项保留来源模块和校验值，读取资料表时核对压缩文件的 SHA-256。

`__init__`、`bindict_proxy`、`deco_skin_index` 和 `skin_bg_index` 的静态记录未提取。玩法筛选根据客户端表名归类，可在全部玩法中搜索每张表。客户端表含历史活动和内部记录，区服开放、入场资格和服务器结算须以实机为准。静态表可供核对规则与输入，100% 通关和动画耗时仍需战斗回放及可达分支证据。

通用 PvE 的默认场景按 `CommonPveBattleEngine.__init__` 读取 `BattleMonstersInfo.resindex`，缺省值为 11032。目录连到 `Combinesceneinfo.battlesceneinfo` 指定的站位，17,603 个关卡已核对完整链路。礁石 `3345301` 的默认场景为 819，站位配置为 418。界面可展开我方与敌方的原始坐标。采用独立引擎或动态场景的副本仍以其自身路径为准。

地图探索按 `MapLevelWindowNew.on_click_exploration` 将入口 `mapnpc.battle_id` 交给 `ExploreBattle` 作为地图 ID。`ExploreBattle.fectchMapStrFromMap` 按 `story_room.MapEntryID` 和难度选地图，`attackMonster` 将具体战斗点的 `MonsterID` 用作 PvE 参数，`cacheScene` 也用该值查询敌方编组。28 个剧情章节可进入对应的地图配置。425 个静态战斗点均能查到敌方编组和站位，其中 17 个配置在地图 ID 999 下，原表未将该 ID 关联到剧情章节。阴阳之理的“大天狗挑战难度1”战斗点为 1801，对应 PvE 和编组 31811、战斗站位 301。区服实际刷出的战斗点由游戏下发的 `MAPNPC_BUFF_INFO` 决定。

`PanelCombat.refreshCombatTipsBtn` 以 `pve_data_flag` 查询 `normal_battle_tips.rule_key`。`PanelCombat.onBtnCombatTips` 读取 `dungeon_challenge_series.fbtips`，并可在战斗条件满足时替换此键。`CommonTipPanel` 先查 `system_rule_dsc`，再查 `tipsInfoData_cn`。御契按此顺序关联了 13 条通用战斗提示与 514 条秘闻默认提示，其中 327 条秘闻提示来自第二张表。该表由 `com/data/pdata/tipsInfoData_cn.py` 的字面量映射提取，原模块 marshal SHA-256 为 `1f3218f2809e2604c87e14a012b81716ebfc74762d0a5a0d5a5c96026140bf28`。界面展示去掉色标后的正文，同时保留完整原字段。

从 `SceneManager._initMapSrc` 提取了 630 条初始场景注册，其中 145 个模式对应的 133 个场景直接声明 `EngineClassName`。例如通用 PvE（3）声明 `MonstarGuanKaEngine`，觉醒（29）声明 `AwakeFbEngine`，阴阳寮首领退治模式（306）声明 `GuildBossEngine`。可按引擎名搜索并展开查看场景脚本与校验值。123 个有直接声明且无模式默认表记录的模式已加入关卡搜索。客户端本地开场可走组队注册、特殊副本或场景自身入口，远程战斗还取决于服务器数据。

从 `team_helper` 加载的组队脚本提取了 304 条组队类型到战斗模式的直接注册，其中 303 条含直接返回的战斗引擎名。164 个战斗模式默认配置有对应的组队入口。`act_team_battle` 中 11 条活动配置均能从组队类型追到引擎和同版默认规则。

京畿净化可按金币、经验、御魂和觉醒查到 2,240 条原版战斗参数，详情展示棋盘编号、数值和权重。`DynamicConfigData` 分别注册四张 `journey_normalbattle_*` 参数表，御契保留各表的独立编号。普通战斗的 `SeaDailyFightPanel.init_ui` 通过当前棋格查询独立的 `DATA_JOURNEY_NORMAL_BATTLE`，再用该记录的 `battle_id` 查询体力和首领预览。本地快照未找到该面板所读的 `journey_normalbattle` 表，普通战斗的实际入场编组仍待核对。`DynamicConfigData` 的 marshal SHA-256 为 `69cc6063aba5d4fc5d797f2e9ab59b3a0af2bca22fb57515d6eb1140f8744baf`。

### 通用 PvE 库存离线复跑

`tools/verify-pve-stage.py` 按 `MonsterGuanKaScene` 声明的 `MonstarGuanKaEngine` 跑模式 3 的本地单人战斗。按 `pve_stage_data.shishentotal` 核对上阵人数，并在原版选角阶段确认每个式神、实际穿戴和自动施法设置。输入沿用 `onmyoji`、`members` 和可选 `spirit` 的库存配装结构。脚本拒绝缺少敌方编组、剧情固定阵容和替换或禁用阴阳师的关卡。独立玩法入口需要另行核对其实际引擎与入场条件。

$env:PYTHONHASHSEED = '0'

## 从本机解包资源生成

使用「阴阳师解包」导出的安装包及云资源，保留 `raw/extra/thd`、`raw/extra/script3.zip` 和 `raw/extra/update.ini`。从「阴阳师培育」的本地分析项目指定 `tools` 和含已验证 opcode 映射的目录。提取工具需要 CPython 3.11.6 及该分析项目的依赖。若原生库校验值与 opcode 证据不符，须使用该版本对应的证据。

```powershell
& $YuqiPython tools/extract-dungeon-catalog.py $YuqiSnapshot --game-tools $YuqiGameTools --opcode-proof $YuqiOpcodeProof --apk-version 2.8.87 --tables tmp/dungeon-tables --output data/dungeon-catalog
```

已提取的 JSON 表也可以直接打包。

```powershell
python tools/build_dungeon_catalog.py tmp/dungeon-tables data/dungeon-catalog
```

运行提取命令时可追加 `--battle-index output/battle-modules.json`，为本版本的 6,942 个战斗模块记录资源路径、偏移和校验值。该索引可定位同一版本的模块，客户端原始文件仍位于解包目录。

## 复跑原版引擎的合成对局

提取时追加 `--script-index tmp/active-scripts.json`，让原版引擎使用从同一资源包提取的脚本和模型。通过下列命令运行晴明与两名帚神的合成对局。

```powershell
$env:PYTHONHASHSEED = '0'
& $YuqiPython tools/verify-rune-runtime.py --snapshot $YuqiSnapshot --game-tools $YuqiGameTools --opcode-proof $YuqiOpcodeProof --script-index tmp/active-scripts.json --output tmp/rune-runtime.json
```

脚本会检查原生库和脚本校验值、禁止网络连接，输出阶段、已过波次、随机调用计数和战斗记录。Windows 宿主使用从相同资源解出的静态字典来适配原版数据表查找。此夹具用于验证结算链路，使用合成角色数据，未测客户端渲染时间或可达随机分支。

本机复跑依次经过加载、准备、召唤、选式神、战斗和结算。合成阵容两回合后在第一波落败。2026-11-26 的回放包含 830 行，全部 39 条播放动作指令均找到对应的模型动画长度。按回放时间和模型长度计算，不同实体的动作窗口共重叠 8,229.01 毫秒，同时最多 4 个实体。

`animationSync` 保留播放指令按模型原始时长计算的窗口。`GameSceneBattleRender.rd_playActionAnim` 在收到新指令时重设同步截止时间，对多段动作累加原始长度，既有截止时间可被下一条较短动作覆盖。`LocalBattleRender` 的本地消息循环依次处理已到队列的指令。

`animationPlayback` 按 `AnimComp.playActionAnim`、`appendNextAnim` 和 `_playNextAnim` 投影每段播放。显式播放速率用于换算片段长度，后续片段在前一段完成时解析当时的别名。收到替换、停止或实体移除记录时截断旧的片段。已用原版 Python 代码和替代渲染回调确认上述顺序。对应 `entities/components/AnimComp.py` 的 marshal SHA-256 为 `e0c661f56b5d200dd5d25114f10e705edadef22b0cd5fa93192e6b680ecd35f4`。循环衔接、冻结恢复、找不到模型动作时会留下不完整提示。投影将动作回调与同毫秒的下一条消息按先回调处理，模型帧、混合、特效与全局倍速仍需实机核对。

交战计时取原版 `bt_battleState(BS_STARTED)` 到 `tn_battleEnded` 的时间差。真实库存种子 0 的引擎全程为 151.08 秒，开战至结算为 139.98 秒。477 段有正时长的动作中有 184 段提前结束，38 次受击请求缺少对应模型动作。在可解析片段上，交战重叠估算为 87.22 秒。按整段请求时长叠加的旧值为 122.69 秒。翻转序号 79 的回放为 135.92 秒交战时间和 77.71 秒重叠。动作重叠包含待机和受击，速度排序继续沿用采样的引擎全程时间，等待实机校准。

`python tools/rune_replay.py tmp/rune-runtime.json --animation-playback --output tmp/rune-animation.json` 可按报告中的 SHA-256 重新校验回放和模型，再生成逐段播放投影。

### 追踪原版引擎随机调用

命令可加 `--seed` 复跑一个明确的 32 位种子。工具使用客户端自带的 `battleengine.battle_tools.RandomRecord` 捕获战斗引擎随机实例的调用位置和返回值，记录在 `randomTrace`。`randomCalls` 对应这段记录的长度，`engineRandomCounter` 则保留引擎原有计数。

同一份带真实契灵的配置以种子 0 和 1 复跑，原有计数两次均为 0，原版记录器分别捕获到 183 次和 164 次调用。两次分别在第 3 和第 4 回合落败。额外观察另一套真实库存种子 0 的 Python 全局随机实例，记录到 `ObjectId` 初始化的四次取位及 `BattleEngine.__init__` 第 577 行生成一次默认种子。原版引擎初始化时按指定种子重设战斗实例。观察前后 1,517 条战斗随机调用和回放散列一致。这项检查只覆盖该次执行路径。

资源 `0.0.816` 的常规单人本地入口已核对到种子来源。`DungeonMember.dungeon_rune_attack_return` 第 55 行进入 `MODE_RUNE_FB`（27），只交给 `enterMainUi` 副本 ID、奖励映射和场景 ID。`SceneManager.beginBattle` 第 1533 行为本地配置创建引擎。`RuneFbEngine` 和 `PveBattleEngine` 的初始化沿用 `BattleEngine`，其构造函数在第 577 行取 `int(random.random() * 10000)`，即 0 至 9999。`BattleEngine.init` 第 1303 至 1314 行只在列出的 PvP 模式检查用户数据里的 `seed`，御魂模式直接用构造函数的种子初始化战斗随机实例。离线工具在调用原版 `init` 前直接指定该值。这个范围针对已核对的本地入口，混合和远端战斗仍待单独验证。`DungeonMember.py` 和 `BattleEngine.py` 的 marshal SHA-256 分别为 `8bbec16f11eaa2c578ee569fc4d0c180b59d9be4f1cb7d51e72cf76fd3f6cc16`、`5333880a15e43334b4c4f81597974a7bf9dd04bf001c8203e91656c8404b278b`。

`--fixed-step-ms 20` 可用客户端 `EngineState.RECORD_MODE` 的固定步长时钟加快单种子复跑。报告的 `clock` 记录步长、更新次数和引擎时间。对同一份真实库存配置，种子 0 和 1 的固定步长模式分别更新 1821 次和 1671 次，随机调用轨迹、胜负和回合数均与各自的实时时钟复跑一致。该模式的时长用于复跑调试，实际客户端的动画、输入和结算计时仍需实机验收。

固定步长下可加 `--audit-random`。报告的 `randomAudit` 逐次记录随机方法、调用位置和观察到的直接大小比较。桌面应用在库存候选的固定步长复跑中显示这些计数。`uniform`、目标选择与洗牌等调用目前仅计入其他随机调用。

检查某次判断的另一结果时，可使用同一配置和种子，追加 `--audit-random --random-reference tmp/rune-audit.json --flip-random 79`，并用另一输出文件保存结果。`79` 是参考报告 `reversibleDraws` 中待检查的序号。继续用翻转后的报告作参考，选择最后一次干预之后实际出现的可翻转判断，即可测试联合变化。`randomAudit.interventions` 记录每次干预及原始随机值。工具校验资源、阵容、种子及步长，重放已有干预并核对新的目标之前的调用记录，最后检查当次同一阈值的判断确实翻转。各次干预均保留原始生成器推进。联合变化的路径仍须验证是否有原生种子可达。

在一份通过魂王的本机库存上，带观察与普通复跑得到一致的回放散列、胜负、用时、生命变化和动画窗口。种子 0 的 1,517 次调用中，1,271 次捕获了大小比较，其中 193 次符合单次翻转条件。分别翻转序号 79、223、270 后均通过三波，其中序号 79 将回合数从 30 改为 27，引擎用时从 151.08 秒变为 147.02 秒。

候选队伍通过采样后，可在「查看随机调用记录」里点「测试随机判断」。御契重新复跑有可翻转判断的第一个采样种子，最多逐次测试 8 个判断。每波存在可翻转的战斗判断时，先从该波选一个，并尽量选不同的调用位置。剩余名额用于补充其他位置、波次或判断方向。`BattleEngine.eggs` 和 `BattleEngine.new_eggs` 在 `0.0.816` 只走开场特效和画面标志路径，排在战斗判断之后。若第一或第二波的单次翻转改变了回放、仍通关，而且新路径出现后续波次的可翻转判断，御契选其中耗时最长的回放接着做一次联合测试。界面显示每次测试的波次、回合、引擎用时和结算，可随时停止并保留已经返回的结果。

对上述本机库存，早期按调用位置排序的批量测试覆盖前两波的 8 次判断，8 次均通过三波。引擎用时为 147.02–304.78 秒。序号 288 的增益判断将回合从 30 增至 63，引擎用时从 151.08 增至 304.78 秒。

改用三波优先顺序后，同一库存和种子 0 的 8 次测试覆盖第 1、2、3 波，均通过三波，引擎用时为 146.92–304.78 秒。三个波次最先测试的调用序号分别为 79、706、1036。

现在可接着沿第 1 波序号 288 翻转后的路径，在第 2 波翻转序号 611（`SkillComp_20036._afterDoSkillCalcCallback` 的 0.4 概率判断）。本机原版引擎通过三波，共 63 回合、304.78 秒，与只翻转 288 时的回合数和引擎用时相同。未修改随机判断的基准为 30 回合、151.08 秒。

### 复跑选定库存

在上面的命令末尾加 `--team tmp/selected-team.json`，即可将选定库存交给原版引擎。文件的 `onmyoji` 是明确指定的阴阳师配置，包含 `heroId`、`level`、`star`、`awake` 与 `skinfo`。`members` 数组里每项包含 `instanceId`、平安志原始式神 `hero` 和选定御魂记录数组 `souls`。可以少于五名式神，或保留空余御魂位置。每件御魂和每个式神实例至多使用一次，同一只式神的御魂槽位不能重复。

式神培养信息使用原版 `HeroData`。御魂导出值映射为 `EquipAttrCalc` 的属性名，套装效果由原版按套装 ID 处理。首领御魂的固定值通过导出属性计入一次。回放用临时别名代替库存实例 ID。

`onmyoji` 和 `members` 每项可设置 `aiSkill`。已知自动施法值通过原版 `op_setAutoSkill` 应用，报告记录实际装载的技能和已应用的设置。开启技能选择后，一名真实账号式神、六件真实御魂及测试晴明在第一波经五回合结算为失败，原版报告写明胜负。全随机分支证明仍待接入。

阵容码配置契灵时，桌面端按客户端 `TAHelper.check_hunling_can_use` 的种类、最低星级、最低等级和术印重复数量核对库存。当前每个原码先复跑一个符合要求的库存实例，优先选择额外星级、等级和术印较少的实例。原版 `HunlingAttrCalc` 提供技能映射，战斗引擎计算并应用实际实例的属性。本机已用真实库存中的六星契灵、真实式神和六件真实御魂跑到结算。报告记录到 18% 防御加成和三个实际附加的术印技能，阵容在第一波落败。

### 原码试完后的库存备选

勾选的阵容都已核对且没有取得通关结果时，可以点击「从库存寻找备选」。未勾选阵容时可直接使用。根据本版本的技能说明和三波敌方开场属性，程序从库存搭配开场输出、尾刀、供火、控制和恢复。魂王的「罪凝」会扣减生命，低于 70% 生命时造成的伤害降低 70%，所以备选优先尝试萤草等具备群体治疗的式神。每队使用五个独立式神实例及三十件互不重复的御魂，最多送六队进原版引擎。平安志导出缺少实际阴阳师培养，复跑使用 60 级晴明和满级言灵·星、言灵·守，优先施放言灵·星，只配备导出中已核对的晴明契灵。

每队复跑同一组种子，遇到未通关的样本便停在该队。界面列出各场的胜负、通过波数、引擎全程时间、开战至结算时间，以及可解析片段的动作重叠估算。通过全部采样的队伍按最慢一场排序。参与比较的队伍各场均有开战及结算时间时统一使用该段时间。有任一场缺失时统一使用引擎全程时间。界面给出最慢种子和采用的时间口径。该排序和结论仅覆盖这组采样。复跑报告的 `monsterHealth` 从原版创建、属性和波次消息归纳每波敌人的初始、最低、结束生命值及生命回升。生命回升累计包括治疗、复活及其他让生命增加的变化。已有报告可用 `python tools/rune_replay.py <报告> --monster-health --output <输出>` 校验回放摘要。

勾选原码和库存备选通过首轮采样后，可以补测 0 至 23 中剩余的 19 个原生种子。补测复用原配装与固定步长，随机判断由客户端引擎自行生成。停止后可从下一个种子继续，未取得结算的种子会重试。当前软件会话内，同一库存和配装重跑时沿用补测记录。实际遇到失败时，该备选不再提供阵容码操作，勾选原码均失败时可转入库存搜索。会话结束后不保留补测记录。

资源 `0.0.816` 的一套真实库存配装完成了种子 0 至 23、42、9998、9999 的未干预复跑，27 个种子均通过三波。原版回报 25 至 32 回合，引擎全程 138.88 至 175.78 秒，最慢为补测种子 14。开战到结算为 127.78 至 164.68 秒。本组样本覆盖已核对的本地入口的 27 个初始种子，混合和远端战斗及完整随机分支仍待验证。更正离线工具的种子入口后，重新运行种子 0 和 14，胜负、回合数和时长均与原结果一致。

通过全部采样的备选会自动生成 V3 完整阵容码和二维码。点击「查看阵容码和保存」可以复制完整码。游戏阵容码保存技能、可指定的御魂套装与主属性、面板范围。面板范围按两位小数向外取整，应用阵容后仍需核对实际御魂和阴阳师普攻等级。登录并选择可用角色后，可以在同一处上传并核对官方短码。

「保存到阵容库」会为当前库存保留原版复跑用的式神和御魂引用，并核对码、客户端版本和实际战斗输入。选中已保存的阵容再次复跑时会优先使用原配装，库存或版本有变时回到阵容码精算。旧凭据仍可定位原配装，按当前种子组重新复跑。实例引用只用于当前库存和主动导出的整库备份。二维码、官方上传和单套阵容资料导出只携带阵容信息。共同采样通过的结果在界面上仍标为全随机分支待验证。

### 常规单人本地入口的全种子验收

御魂悲鸣、御魂神罚和御魂虚无通过各自的首轮采样后，勾选原码和库存备选均可点「验收 10,000 个本地种子」。界面显示原版胜利数与当前最慢种子，虚无还显示两波均清场的胜利数。可暂停并关闭软件。重新精算同一配装后会读回原进度，切换账号时只显示当前账号的配装结果。找到原版落败时，失败种子及通过波数会保留，备选阵容码入口会撤下。完成全量的备选优先按验收中最慢一场的引擎全程时间排序。界面记录存在御契本机用户数据的 `rune-seed-evidence` 目录。

也可从命令行离线运行，用独立验收目录并行处理种子。`--dungeon 101` 是悲鸣，`--dungeon 103` 是虚无，省略该参数时使用神罚（`102`）。

```powershell
node tools/verify-rune-seeds.cjs --team <复跑配装JSON> --runtime <本地运行时JSON> --out <验收目录> --dungeon 101 --workers 4
```

`--team` 使用原版复跑的配装输入，含 `onmyoji`、五个 `members` 和可选 `spirit`。虚无在 `rounds` 中按顺序提供两份配装。可加 `--limit` 分批运行。验收目录绑定副本、阵容、御魂配置、资源版本和运行时，重复执行会跳过已核验的种子。Ctrl+C 会保留写完的结果。原版确定落败时会记录种子、波次、回放摘要和耗时，并停止发起新复跑。异常或未知结算会停止本批，重试时仍会计算该种子。记录只保存配装和运行时校验值、种子及结算摘要。

只有 10,000 个种子均获得原版胜利时才返回 `all-local-seeds-passed`。悲鸣和神罚还要求每场都清完三波。虚无沿用基础战斗引擎的 0 至 9999 初始种子，逐场核对两波结算、第二波实际清场和首波结转时限。其范围是当前配装、20 毫秒固定步长、自动施法和已核对的常规单人本地入口。其他入口、客户端真实用时和整个阵容搜索空间仍需分别核对。

在扩展验收的一套真实库存配装中，种子 2016 与 7698 都通过三波，分别用了 61 和 82 回合。引擎开战至结算分别为 282.30 和 416.80 秒。种子 2016 单独复跑的回放校验值与批量结果一致。首轮采样的最慢场次不能确定这套配装的最慢通关时间。

采样战报会列出各波用时。暂停全种子验收后，可以复跑当前最慢或未通关的种子，查看各波用时和敌方生命。御契会核对保存的结算、通过波数和引擎时间，虚无还会核对回放校验值。悲鸣和神罚的各波计时从该波首个敌人进场开始，到原版 `finishedWaveCount` 确认清场为止，未清场的波次显示截至记录结束的时间。各波时间未计入波次之间的间隔。
