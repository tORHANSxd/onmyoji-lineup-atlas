# 全客户端副本资料

御契桌面版在「阵容库 → 全客户端副本与规则」按需读取本地资料。打包前将生成的目录放在 `data/dungeon-catalog`，即可随桌面版打开。运行时也可以在这个面板选择已有的副本资料目录。

「按关卡查找」从同版的资料表列出 31,271 条关卡、战斗模式及玩法参数配置，包括通用 PvE、御魂、真·八岐大蛇、觉醒、秘闻、探索、地域鬼王、契灵之境、六道之门、阴阳寮和历次活动。可按名称、玩法及关卡或编组 ID 搜索。关卡详情连到编组、场景、活动时间、首领及规则文本，点击敌人可核对属性、免疫与该等级的技能说明。原始字段及来源 SHA-256 可展开查看，也可跳转到原表或关联关卡。

有「模拟已知阵容」入口的关卡可从阵容库勾选对应阵容码，再用当前账号库存精算式神和御魂。战报记录配置、随机种子、原版结算和计时。阵容成员可以在「阵容制作器」手动配置并保存完整码。

派生索引和原表分别校验。本版有 95,687 条可解析引用。另有 14 个通用 PvE 关卡指向缺失的敌方编组，ID 为 18 至 26、11111、11112、20110、20719 和 20831，均未出现在 2.8.87 基础 APK 或 `0.0.816` 资源的 `BattleMonstersInfo`。详情保留原编号和缺失提示。索引包含历史、副本变体和内部配置，区服实际开放仍以游戏内状态为准。「查资料表」可继续检索全部原表。旧目录没有派生索引时，面板直接打开资料表。

《阴阳师》2.8.87 的 `0.0.816` 资源包中，已从 3,851 个客户端配置模块读取 3,847 张表，共 659,646 条记录。另有两张由战斗脚本提取的注册表，包含 934 条记录。主要资料包括 17,617 条通用 PvE 关卡、17,563 条战斗编组、491 条场景站位、217 条通用战斗模式以及御魂、觉醒、秘闻、阴阳寮狭间暗域、活动组队等玩法专表。表项保留来源模块和校验值，读取资料表时核对压缩文件的 SHA-256。

`__init__`、`bindict_proxy`、`deco_skin_index` 和 `skin_bg_index` 的静态记录未提取。玩法筛选根据客户端表名归类，可在全部玩法中搜索每张表。客户端表含历史活动和内部记录，区服开放、入场资格和服务器结算须以实机为准。静态表可供核对规则与输入，100% 通关和动画耗时仍需战斗回放及可达分支证据。

### 地域鬼王

同版 `lbs_world_boss_area` 的 133 个地点可查分区、首领模板、战斗候选编组与站位。普通难度的静态表共有 798 个带权重的候选条目，详情展示条件说明模板和参数池。密歇根湖的条件 80023 在原表各出现一次权重 0.1，界面并列显示两项权重。原版 `AreaKingLogic.getSpecialAttacksByBossAreaId` 从 `dailybossinfo` 获取实际的每日条件及参数。国王湖的静态候选关卡为 300092，条件 10003 的模板是限定回合，参数池为 61 和 70。

### 通用 PvE 库存离线复跑

在「阵容库 → 全客户端副本与规则 → 按关卡查找」打开已接入原版引擎的关卡，在「模拟已知阵容」选择一套已完整解析的阵容，也可使用阵容库已勾选项。已核对阵容码分类的关卡只接收对应分类。没有阵容码分类映射的关卡可从下拉列表指定人数匹配的已知阵容。开始后使用当前账号库存按原码要求配装。

通用 PvE 按种子 0、1、2、3、7、42 使用原版引擎模拟。耗时关卡按共同种子中最慢一场排序，计分关卡按限时窗口内的伤害比较。可查看每场的结算、回合、波次和动作重叠估算，停止后保留已取得的战报。切换库存账号或关卡会清除当前结果。

用真实平安志库存为配置 31811 生成六套备选，首批实测的两套均通过六个采样种子。当前穿戴方案最慢用时 11.22 秒，双输出与供火方案最慢用时 6.62 秒，均为引擎开战至结算。该关卡尚无已核对的官方阵容码映射，桌面端提供采样战报。

`tools/verify-pve-stage.py` 按 `MonsterGuanKaScene` 声明的 `MonstarGuanKaEngine` 跑模式 3 的本地单人战斗。按 `pve_stage_data.shishentotal` 核对上阵人数，并在原版选角阶段确认每个式神、实际穿戴和自动施法设置。输入沿用 `onmyoji`、`members` 和可选 `spirit` 的库存配装结构。脚本拒绝缺少敌方编组、剧情固定阵容和替换或禁用阴阳师的关卡。独立玩法入口需要另行核对其实际引擎与入场条件。

```powershell
$env:PYTHONHASHSEED = '0'
& $YuqiPython tools/verify-pve-stage.py --runtime <本地运行时JSON> --team <库存配装JSON> --suit-index <御魂套装JSON> --stage 3345301 --seed 0 --output <战报JSON>
```

### 追踪原版引擎随机调用

命令可加 `--seed` 复跑一个明确的 32 位种子。工具使用客户端自带的 `battleengine.battle_tools.RandomRecord` 捕获战斗引擎随机实例的调用位置和返回值，记录在 `randomTrace`。`randomCalls` 对应这段记录的长度，`engineRandomCounter` 则保留引擎原有计数。

同一份带真实契灵的配置以种子 0 和 1 复跑，原有计数两次均为 0，原版记录器分别捕获到 183 次和 164 次调用。两次分别在第 3 和第 4 回合落败。额外观察另一套真实库存种子 0 的 Python 全局随机实例，记录到 `ObjectId` 初始化的四次取位及 `BattleEngine.__init__` 第 577 行生成一次默认种子。原版引擎初始化时按指定种子重设战斗实例。观察前后 1,517 条战斗随机调用和回放散列一致。这项检查只覆盖该次执行路径。

资源 `0.0.816` 的常规单人本地入口已核对到种子来源。`DungeonMember.dungeon_rune_attack_return` 第 55 行进入 `MODE_RUNE_FB`（27），只交给 `enterMainUi` 副本 ID、奖励映射和场景 ID。`SceneManager.beginBattle` 第 1533 行为本地配置创建引擎。`RuneFbEngine` 和 `PveBattleEngine` 的初始化沿用 `BattleEngine`，其构造函数在第 577 行取 `int(random.random() * 10000)`，即 0 至 9999。`BattleEngine.init` 第 1303 至 1314 行只在列出的 PvP 模式检查用户数据里的 `seed`，御魂模式直接用构造函数的种子初始化战斗随机实例。离线工具在调用原版 `init` 前直接指定该值。这个范围针对已核对的本地入口，混合和远端战斗仍待单独验证。`DungeonMember.py` 和 `BattleEngine.py` 的 marshal SHA-256 分别为 `8bbec16f11eaa2c578ee569fc4d0c180b59d9be4f1cb7d51e72cf76fd3f6cc16`、`5333880a15e43334b4c4f81597974a7bf9dd04bf001c8203e91656c8404b278b`。

`--fixed-step-ms 20` 可用客户端 `EngineState.RECORD_MODE` 的固定步长时钟加快单种子复跑。报告的 `clock` 记录步长、更新次数和引擎时间。对同一份真实库存配置，种子 0 和 1 的固定步长模式分别更新 1821 次和 1671 次，随机调用轨迹、胜负和回合数均与各自的实时时钟复跑一致。该模式的时长用于复跑调试，实际客户端的动画、输入和结算计时仍需实机验收。

固定步长下可加 `--audit-random`。报告的 `randomAudit` 逐次记录随机方法、调用位置和观察到的直接大小比较。桌面应用在库存候选的固定步长复跑中显示这些计数。`uniform`、目标选择与洗牌等调用目前仅计入其他随机调用。

检查某次判断的另一结果时，可使用同一配置和种子，追加 `--audit-random --random-reference tmp/rune-audit.json --flip-random 79`，并用另一输出文件保存结果。`79` 是参考报告 `reversibleDraws` 中待检查的序号。继续用翻转后的报告作参考，选择最后一次干预之后实际出现的可翻转判断，即可测试联合变化。`randomAudit.interventions` 记录每次干预及原始随机值。工具校验资源、阵容、种子及步长，重放已有干预并核对新的目标之前的调用记录，最后检查当次同一阈值的判断确实翻转。各次干预均保留原始生成器推进。联合变化的路径仍须验证是否有原生种子可达。

在一份通过魂王的本机库存上，带观察与普通复跑得到一致的回放散列、胜负、用时、生命变化和动画窗口。种子 0 的 1,517 次调用中，1,271 次捕获了大小比较，其中 193 次符合单次翻转条件。分别翻转序号 79、223、270 后均通过三波，其中序号 79 将回合数从 30 改为 27，引擎用时从 151.08 秒变为 147.02 秒。

现在可接着沿第 1 波序号 288 翻转后的路径，在第 2 波翻转序号 611（`SkillComp_20036._afterDoSkillCalcCallback` 的 0.4 概率判断）。本机原版引擎通过三波，共 63 回合、304.78 秒，与只翻转 288 时的回合数和引擎用时相同。未修改随机判断的基准为 30 回合、151.08 秒。

通用 PvE 工作台将我方的原版伤害浮动取下限。资源 `0.0.816` 的 `com.utils.formula.calcRawAttackDmg` 将伤害乘以 `1 + uniform(-浮动, 浮动)`，这里在原版调用点取 `1 - abs(浮动)`，仍消耗对应的一次原始随机调用。敌方伤害和暴击、目标、效果命中等其他随机判定按原版复跑。战报记录使用下限的次数。御魂验收记录将伤害口径与配装一起校验。

每队复跑同一组种子，遇到未通关的样本便停在该队。界面列出各场的胜负、通过波数、引擎全程时间、开战至结算时间，以及可解析片段的动作重叠估算。通过全部采样的队伍按最慢一场排序。参与比较的队伍各场均有开战及结算时间时统一使用该段时间。有任一场缺失时统一使用引擎全程时间。界面给出最慢种子和采用的时间口径。该排序和结论仅覆盖这组采样。复跑报告的 `monsterHealth` 从原版创建、属性和波次消息归纳每波敌人的初始、最低、结束生命值及生命回升。生命回升累计包括治疗、复活及其他让生命增加的变化。已有报告可用 `python tools/rune_replay.py <报告> --monster-health --output <输出>` 校验回放摘要。

勾选原码通过首轮采样后，可以补测 0 至 23 中剩余的 19 个原生种子。补测复用原配装与固定步长，随机判断由客户端引擎自行生成。停止后可从下一个种子继续，未取得结算的种子会重试。当前软件会话内，同一库存和配装重跑时沿用补测记录，有失败时记录实际落败种子。会话结束后清除补测记录。

资源 `0.0.816` 的一套真实库存配装完成了种子 0 至 23、42、9998、9999 的未干预复跑，27 个种子均通过三波。原版回报 25 至 32 回合，引擎全程 138.88 至 175.78 秒，最慢为补测种子 14。开战到结算为 127.78 至 164.68 秒。本组样本覆盖已核对的本地入口的 27 个初始种子，混合和远端战斗及完整随机分支仍待验证。更正离线工具的种子入口后，重新运行种子 0 和 14，胜负、回合数和时长均与原结果一致。

已有复跑配装凭据的阵容可按当前账号恢复保存的式神和御魂。库存或版本有变时回到阵容码精算。实例引用只用于当前库存和主动导出的整库备份。需要手动制作新阵容码时使用「阵容制作器」。

### 常规单人本地入口的全种子验收

御魂悲鸣、御魂神罚和御魂虚无通过各自的首轮采样后，可对已知配装点「验收 10,000 个本地种子」。界面显示原版胜利数与当前最慢种子，虚无还显示两波均清场的胜利数。可暂停并关闭软件。重新精算同一配装后会读回原进度，切换账号时只显示当前账号的配装结果。找到原版落败时，保留失败种子及通过波数。界面记录存在御契本机用户数据的 `rune-seed-evidence` 目录。

也可从命令行离线运行，用独立验收目录并行处理种子。`--dungeon 101` 是悲鸣，`--dungeon 103` 是虚无，省略该参数时使用神罚（`102`）。

```powershell
node tools/verify-rune-seeds.cjs --team <复跑配装JSON> --runtime <本地运行时JSON> --out <验收目录> --dungeon 101 --workers 4
```

`--team` 使用原版复跑的配装输入，含 `onmyoji`、五个 `members` 和可选 `spirit`。虚无在 `rounds` 中按顺序提供两份配装。可加 `--limit` 分批运行。验收目录绑定副本、阵容、御魂配置、资源版本和运行时，重复执行会跳过已核验的种子。Ctrl+C 会保留写完的结果。原版确定落败时会记录种子、波次、回放摘要和耗时，并停止发起新复跑。异常或未知结算会停止本批，重试时仍会计算该种子。记录只保存配装和运行时校验值、种子及结算摘要。

只有 10,000 个种子均获得原版胜利时才返回 `all-local-seeds-passed`。悲鸣和神罚还要求每场都清完三波。虚无沿用基础战斗引擎的 0 至 9999 初始种子，逐场核对两波结算、第二波实际清场和首波结转时限。其范围是当前配装、20 毫秒固定步长、自动施法和已核对的常规单人本地入口。其他入口、客户端真实用时和整个阵容搜索空间仍需分别核对。

在扩展验收的一套真实库存配装中，种子 2016 与 7698 都通过三波，分别用了 61 和 82 回合。引擎开战至结算分别为 282.30 和 416.80 秒。种子 2016 单独复跑的回放校验值与批量结果一致。首轮采样的最慢场次不能确定这套配装的最慢通关时间。

采样战报会列出各波用时。暂停全种子验收后，可以复跑当前最慢或未通关的种子，查看各波用时和敌方生命。御契会核对保存的结算、通过波数和引擎时间，虚无还会核对回放校验值。悲鸣和神罚的各波计时从该波首个敌人进场开始，到原版 `finishedWaveCount` 确认清场为止，未清场的波次显示截至记录结束的时间。各波时间未计入波次之间的间隔。

同一套配装的对照结果如下，单位为秒。第二波动作重叠量来自原版动作记录在该波内的模型播放投影。

| 种子 | 第一波 | 第二波 | 第三波 | 第二波动作重叠估算 |
| --- | ---: | ---: | ---: | ---: |
| 42 | 23.10 | 53.76 | 49.90 | 30.83 |
| 2016 | 39.04 | 126.98 | 115.26 | 72.33 |
| 7698 | 46.20 | 265.08 | 104.50 | 132.59 |

种子 7698 单独复跑与批次回放校验值一致。第二波三个敌人的生命回升分别约为 498,666、341,838 和 448,386，其中 3 号位敌人的生命两次从零回到正值。记录显示耗时集中于第二波，并保留生命变化供核对。

同一套配装的批量验收在种子 8929 找到确定落败，最终保存 293 次通关和 1 次落败。该场只通过第一波，52 回合后落败，开战至结算 452.54 秒。独立复跑得到同一回放校验值。另一套库存配装在相同种子通过三波，开战至结算 151.96 秒，并通过九个共同种子，其中最慢一场为种子 2 的 166.02 秒。
