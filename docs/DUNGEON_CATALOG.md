# 全客户端副本资料

御契桌面版在「阵容库 → 全客户端副本与规则」按需读取本地资料。打包前将生成的目录放在 `data/dungeon-catalog`，即可随桌面版打开。运行时也可以在这个面板选择已有的副本资料目录。

「按关卡查找」从同版的 135 张表列出 28,416 条关卡相关配置，包括通用 PvE、御魂、觉醒、秘闻、探索、地域鬼王、契灵、六道之门、阴阳寮和历次活动。可按名称、玩法及关卡或编组 ID 搜索。关卡详情连到编组、场景、活动时间、首领及规则文本，点击敌人可核对属性、免疫与该等级的技能说明。原始字段及来源 SHA-256 可展开查看，也可跳转到原表。

派生索引和原表分别校验。本版核对了 90,619 条可解析的引用，另有 203 条引用指向未找到的 14 个战斗编组，详情按引用单独提示。索引统计含历史、副本变体和内部配置，区服实际开放仍以游戏内状态为准。「查资料表」可继续检索全部原表。旧目录没有派生索引时，面板直接打开资料表。

《阴阳师》2.8.87 的 `0.0.816` 资源包中，已从 3,851 个客户端配置模块读取 3,847 张表，共 659,646 条记录。主要资料包括 17,617 条通用 PvE 关卡、17,563 条战斗编组、491 条场景站位、217 条通用战斗模式以及御魂、觉醒、秘闻、阴阳寮狭间暗域、活动组队等玩法专表。表项保留来源模块和校验值，读取资料表时核对压缩文件的 SHA-256。

`__init__`、`bindict_proxy`、`deco_skin_index` 和 `skin_bg_index` 的静态记录未提取。玩法筛选根据客户端表名归类，可在全部玩法中搜索每张表。客户端表含历史活动和内部记录，区服开放、入场资格和服务器结算须以实机为准。静态表可供核对规则与输入，100% 通关和动画耗时仍需战斗回放及可达分支证据。

通用 PvE 的默认场景按 `CommonPveBattleEngine.__init__` 读取 `BattleMonstersInfo.resindex`，缺省值为 11032。目录连到 `Combinesceneinfo.battlesceneinfo` 指定的站位，17,603 个关卡已核对完整链路。礁石 `3345301` 的默认场景为 819，站位配置为 418。界面可展开我方与敌方的原始坐标。采用独立引擎或动态场景的副本仍以其自身路径为准。

`PanelCombat.refreshCombatTipsBtn` 以 `pve_data_flag` 查询 `normal_battle_tips.rule_key`。`PanelCombat.onBtnCombatTips` 读取 `dungeon_challenge_series.fbtips`，并可在战斗条件满足时替换此键。`CommonTipPanel` 先查 `system_rule_dsc`，再查 `tipsInfoData_cn`。御契按此顺序关联了 13 条通用战斗提示与 514 条秘闻默认提示，其中 327 条秘闻提示来自第二张表。该表由 `com/data/pdata/tipsInfoData_cn.py` 的字面量映射提取，原模块 marshal SHA-256 为 `1f3218f2809e2604c87e14a012b81716ebfc74762d0a5a0d5a5c96026140bf28`。界面展示去掉色标后的正文，同时保留完整原字段。

## 从本机解包资源生成

使用「阴阳师解包」导出的安装包及云资源，保留 `raw/extra/thd`、`raw/extra/script3.zip` 和 `raw/extra/update.ini`。从「阴阳师培育」的本地分析项目指定 `tools` 和含已验证 opcode 映射的目录。提取工具需要 CPython 3.11.6 及该分析项目的依赖。若原生库校验值与 opcode 证据不符，须使用该版本对应的证据。

```powershell
& $YuqiPython tools/extract-dungeon-catalog.py $YuqiSnapshot --game-tools $YuqiGameTools --opcode-proof $YuqiOpcodeProof --apk-version 2.8.87 --tables tmp/dungeon-tables --output data/dungeon-catalog
```

已提取的 JSON 表也可以直接打包。

```powershell
python tools/build_dungeon_catalog.py tmp/dungeon-tables data/dungeon-catalog
```

运行提取命令时可追加 `--battle-index output/battle-modules.json`，为本版本的 6,942 个战斗模块记录资源路径、偏移和校验值。该索引可定位同一版本的模块，客户端原始文件仍位于解包目录。

## 复跑原版引擎的合成对局

提取时追加 `--script-index tmp/active-scripts.json`，让原版引擎使用从同一资源包提取的脚本和模型。通过下列命令运行晴明与两名帚神的合成对局。

```powershell
$env:PYTHONHASHSEED = '0'
& $YuqiPython tools/verify-rune-runtime.py --snapshot $YuqiSnapshot --game-tools $YuqiGameTools --opcode-proof $YuqiOpcodeProof --script-index tmp/active-scripts.json --output tmp/rune-runtime.json
```

脚本会检查原生库和脚本校验值、禁止网络连接，输出阶段、已过波次、随机调用计数和战斗记录。Windows 宿主使用从相同资源解出的静态字典来适配原版数据表查找。此夹具用于验证结算链路，使用合成角色数据，未测客户端渲染时间或可达随机分支。

本机复跑依次经过加载、准备、召唤、选式神、战斗和结算。合成阵容两回合后在第一波落败。2026-11-26 的回放包含 830 行，全部 39 条播放动作指令均找到对应的模型动画长度。按回放时间和模型长度计算，不同实体的动作窗口共重叠 8,229.01 毫秒，同时最多 4 个实体。

`animationSync` 记录客户端播放指令的名义同步窗口，包含动画别名及多段动作的时长。排队指令单独计数，缺少模型或动画时列出未解析的记录。数值包括待机和受击动作请求，尚未测量画面帧、播放速率、取消动作后的实际时长或结算界面计时。排名仍需用实机计时校准。

`python tools/rune_replay.py tmp/rune-runtime.json --output tmp/rune-animation.json` 可按报告中的 SHA-256 重新校验回放和模型，再计算这些窗口。

### 追踪原版引擎随机调用

命令可加 `--seed` 复跑一个明确的 32 位种子。工具使用客户端自带的 `battleengine.battle_tools.RandomRecord` 捕获战斗引擎随机实例的调用位置和返回值，记录在 `randomTrace`。`randomCalls` 对应这段记录的长度，`engineRandomCounter` 则保留引擎原有计数。

同一份带真实契灵的配置以种子 0 和 1 复跑，原有计数两次均为 0，原版记录器分别捕获到 183 次和 164 次调用。两次分别在第 3 和第 4 回合落败。此记录只覆盖战斗引擎的随机实例，模块直接使用的全局随机数和所有可达分支仍需单独验证。

`--fixed-step-ms 20` 可用客户端 `EngineState.RECORD_MODE` 的固定步长时钟加快单种子复跑。报告的 `clock` 记录步长、更新次数和引擎时间。对同一份真实库存配置，种子 0 和 1 的固定步长模式分别更新 1821 次和 1671 次，随机调用轨迹、胜负和回合数均与各自的实时时钟复跑一致。该模式的时长用于复跑调试，实际客户端的动画、输入和结算计时仍需实机验收。

固定步长下可加 `--audit-random`。报告的 `randomAudit` 逐次记录随机方法、调用位置和观察到的直接大小比较。桌面应用在库存候选的固定步长复跑中显示这些计数。`uniform`、目标选择与洗牌等调用目前仅计入其他随机调用。

检查某次判断的另一结果时，可使用同一配置和种子，追加 `--audit-random --random-reference tmp/rune-audit.json --flip-random 79`，并用另一输出文件保存结果。`79` 是参考报告 `reversibleDraws` 中待检查的序号。工具校验资源、阵容、种子及步长，确认回放到该序号前的随机调用记录相符，并检查当次同一阈值的判断确实翻转。该操作保留当次原始生成器推进，仅替换交给引擎的这个值。翻转测试不证明存在原生种子可生成该路径，结论也不覆盖多个判断同时变化。

在一份通过魂王的本机库存上，带观察与普通复跑得到一致的回放散列、胜负、用时、生命变化和动画窗口。种子 0 的 1,517 次调用中，1,271 次捕获了大小比较，其中 193 次符合单次翻转条件。分别翻转序号 79、223、270 后均通过三波，其中序号 79 将回合数从 30 改为 27，引擎用时从 151.08 秒变为 147.02 秒。

候选队伍通过采样后，可在「查看随机调用记录」里点「测试随机判断」。御契重新复跑有可翻转判断的第一个采样种子，最多逐次测试 8 个判断。每波存在可翻转的战斗判断时，先从该波选一个，并尽量选不同的调用位置。剩余名额用于补充其他位置、波次或判断方向。`BattleEngine.eggs` 和 `BattleEngine.new_eggs` 在 `0.0.816` 只走开场特效和画面标志路径，排在战斗判断之后。界面逐条显示是否通关、通过波数、回合和引擎时间，并列出已完成测试的波次。可随时停止，保留已经返回的结果。每次从同一基准独立翻转一次，结论仍受随机分支联合可达性与实机计时限制。

对上述本机库存，早期按调用位置排序的批量测试覆盖前两波的 8 次判断，8 次均通过三波。引擎用时为 147.02–304.78 秒。序号 288 的增益判断将回合从 30 增至 63，引擎用时从 151.08 增至 304.78 秒。

改用三波优先顺序后，同一库存和种子 0 的 8 次测试覆盖第 1、2、3 波，均通过三波，引擎用时为 146.92–304.78 秒。三个波次最先测试的调用序号分别为 79、706、1036。

### 复跑选定库存

在上面的命令末尾加 `--team tmp/selected-team.json`，即可将选定库存交给原版引擎。文件的 `onmyoji` 是明确指定的阴阳师配置，包含 `heroId`、`level`、`star`、`awake` 与 `skinfo`。`members` 数组里每项包含 `instanceId`、平安志原始式神 `hero` 和选定御魂记录数组 `souls`。可以少于五名式神，或保留空余御魂位置。每件御魂和每个式神实例至多使用一次，同一只式神的御魂槽位不能重复。

式神培养信息使用原版 `HeroData`。御魂导出值映射为 `EquipAttrCalc` 的属性名，套装效果由原版按套装 ID 处理。首领御魂的固定值通过导出属性计入一次。回放用临时别名代替库存实例 ID。

`onmyoji` 和 `members` 每项可设置 `aiSkill`。已知自动施法值通过原版 `op_setAutoSkill` 应用，报告记录实际装载的技能和已应用的设置。开启技能选择后，一名真实账号式神、六件真实御魂及测试晴明在第一波经五回合结算为失败，原版报告写明胜负。全随机分支证明仍待接入。

阵容码配置契灵时，桌面端按客户端 `TAHelper.check_hunling_can_use` 的种类、最低星级、最低等级和术印重复数量核对库存。当前每个原码先复跑一个符合要求的库存实例，优先选择额外星级、等级和术印较少的实例。原版 `HunlingAttrCalc` 提供技能映射，战斗引擎计算并应用实际实例的属性。本机已用真实库存中的六星契灵、真实式神和六件真实御魂跑到结算。报告记录到 18% 防御加成和三个实际附加的术印技能，阵容在第一波落败。

### 在桌面软件复跑勾选阵容

本机运行时须能读取同一资源版本的客户端快照、脚本索引和匹配的原生库证据。创建本地 `rune-runtime.json`，填写以下五个绝对路径：

| 字段 | 本地位置 |
|---|---|
| `python` | 能运行本节工具和游戏资源依赖的 Python 3.11 可执行文件 |
| `snapshot` | 解包工具生成的客户端快照目录 |
| `gameTools` | 包含 `game_resources.py`、`original_battle.py` 和 `original_host.py` 的工具目录 |
| `opcodeProof` | 包含 `native-evidence.json` 和对应 opcode 映射的目录 |
| `scriptIndex` | 通过 `--script-index` 从同一快照生成的 JSON |

将 `ATLAS_RUNE_RUNTIME` 指向这个文件后启动御契，也可把文件放进便携版的 `resources` 目录。打开「副本资料与库存精算」，在御魂神罚中勾选已经解析的阵容，点击「精算并离线复跑」。原版复跑按单场依次结算，仅接收精算得到的当前库存配装。切换账号会停止旧任务，运行结束后清理临时库存。缺少本机运行时仍可使用库存精算。

勾选阵容和库存备选统一使用 20 毫秒固定步长与种子 0、1、2、3、7、42，按顺序跑到首次落败、未取得结算或全部通过。选中阵容的当前配装出现落败，或库存精算已证明原码约束无解，才计入允许搜索备选的失败条件。全部勾选项都符合失败条件时，界面显示备选入口。超时、未解析和其他资料缺口会显示待核对。已有本机配装的原码也重新跑同一组种子。

### 原码试完后的库存备选

勾选的阵容都已核对且没有取得通关结果时，可以点击「从库存寻找备选」。未勾选阵容时可直接使用。根据本版本的技能说明和三波敌方开场属性，程序从库存搭配开场输出、尾刀、供火、控制和恢复。魂王的「罪凝」会扣减生命，低于 70% 生命时造成的伤害降低 70%，所以备选优先尝试萤草等具备群体治疗的式神。每队使用五个独立式神实例及三十件互不重复的御魂，最多送六队进原版引擎。平安志导出缺少实际阴阳师培养，复跑使用 60 级晴明和满级言灵·星、言灵·守，优先施放言灵·星，只配备导出中已核对的晴明契灵。

每队按 0、1、2、3、7、42 的顺序复跑，遇到未通关的样本便停在该队。界面列出各场的胜负、通过波数、引擎用时和可解析的动作重叠时长。通过全部采样的队伍按最慢一场的引擎时间排序。该排序和结论均只覆盖这组采样。复跑报告的 `monsterHealth` 从原版创建、属性和波次消息归纳每波敌人的初始、最低、结束生命值及生命回升。生命回升累计包括治疗、复活及其他让生命增加的变化。已有报告可用 `python tools/rune_replay.py <报告> --monster-health --output <输出>` 校验回放摘要。

通过全部采样的备选会自动生成 V3 完整阵容码和二维码。点击「查看阵容码和保存」可以复制完整码。游戏阵容码保存技能、可指定的御魂套装与主属性、面板范围。面板范围按两位小数向外取整，应用阵容后仍需核对实际御魂和阴阳师普攻等级。登录并选择可用角色后，可以在同一处上传并核对官方短码。

「保存到阵容库」会为当前库存保留原版复跑用的式神和御魂引用，并核对码、客户端版本和实际战斗输入。选中已保存的阵容再次复跑时会优先使用原配装，库存或版本有变时回到阵容码精算。实例引用只用于当前库存和主动导出的整库备份。二维码、官方上传和单套阵容资料导出只携带阵容信息。六个采样种子通过的结果在界面上仍标为全随机分支待验证。
