# 平安志库存解析依据

库存解析依据平安志 0.2.8-beta 的 Windows x64 程序。经 REA 标识的 `yys-analysis.exe` SHA-256 为 `4f88390d48510bf9b22d7c3a2affd55ae74076116cf6b36bd61fcb464dba18a4`。以下地址按镜像基址 `0x140000000` 记录。程序已剥离符号，使用 PE 展开表定位函数，再用 Ghidra 定点反编译核对数据流。

| 程序位置 | 核对结果 |
| --- | --- |
| `0x1405bc302` | Tauri 的 `export_character_archive` 命令入口，读取请求，返回记录数与输出目录。 |
| `0x1405bd70c` | 角色档案导出工作函数，校验所选快照归属并读取原始对象。原始对象缺失时走当前数据中的原始 JSON 分支，再交给文件写入路径。 |
| `0x14043d89a` | `CurrentDataDocument` JSON 序列化。独立写入版本、来源、完整度、`rawSha256`、`normalizedSouls`、`normalizedShikigami`、`normalizedItems`、`normalizedRealmCards` 和 `sourcePayload`，另有条件写入的 `integrityMac` 字段。 |
| `0x1404ccb0c` | 当前数据处理路径检查文档版本为 2 后调用上述序列化函数。 |
| `0x14040f786` | 对 `desktop`、`mumu`、`ldplayer`、`bluestacks` 读取 `sourcePayload` 的来源与契灵信息。另有独立的藏宝阁分支。 |
| `0x140427a68` | 构造桌面快照，写入 `yys-desktop-cache-v1`、`souls`、`heroesBagEntries` 和 `hunlings` 等字段。 |
| `0x140424eca` | 一条载荷转换路径先调用桌面快照构造函数，再改写格式为 `mumu-snapshot-v1`，将 `souls` 移入 `hero_equips`。 |
| `0x1404e86a1` | 按类别复制原始快照字段。式神、契灵、御魂及预设分别受导出类别条件控制。 |
| `0x1404e966c` | 原始库存解析分支识别 `mumu-snapshot-v1` 并读取 `hero_equips`，桌面分支识别 `yys-desktop-cache-v1` 并走 `souls`。此函数还处理其他导入来源，其格式需逐个追踪。 |
| `0x1404e98a3` 至 `0x1404e9c7a` | 比较 `yys-analysis-snapshot`、`yys-analysis-snapshot-v1`、`yys-snapshot` 后进入快照分支，共用 `souls` 字段，内部归入原生来源。仅 `mumu-snapshot-v1` 在该分支改读 `hero_equips`。 |
| `0x1405d4f3e` | 分类合并档案构造及保存路径，在顶层写入 `souls`、`format: yys-archive-merge-v1`、`source: archive-merge`、`schemaVersion: 1`、`mergeSources` 和 `scope`，保存时使用 `native` 来源。合并可分别为式神和御魂选择快照版本。 |
| `0x1403fdaa3` 至 `0x1403fdafc` | 读取 `lineupPresets`，检查 `version` 为 1，再进入预设处理路径。 |
| `0x14040c07f`、`0x140409479`、`0x14040c004` | `LineupPresets` 字段分派使用 `soulPlans` 和 `teamPresets`。前者识别 `groups` 和 `plans`，后者识别 `groups` 和 `teams`。 |
| `0x140408784`、`0x14040b31a` | `Team` 读取 `id`、`name`、`heroIds`、`lastUsedAt`。`SoulPlan` 读取 `boxId`、`name`、`equipIds`、`bindings`、`usedAt`。 |
| `0x1404088b6` → `0x14020512a` | 队伍分组的 `teamIds` 是字符串数组。 |
| `0x14040b478` → `0x14040bd63` → `0x14040b299` | 御魂方案分组的 `boxIds` 是无符号 32 位整数数组。方案的 `boxId` 使用同一整数读取函数。 |
| `0x140409e0e` → `0x14040ae1f` → `0x14020532f` | 御魂方案 `bindings` 在类型检查后逐条读取恰好两个字符串。两个位置在客户端中的作用仍待核对。 |

御契使用已识别的原始快照读取式神实例、御魂、契灵和采集范围。对版本 2 缓存，先检查来源属于角色采集，再按 `sourcePayload.format` 选择结构校验，不从采集平台推定快照结构。缓存的 `normalized*` 是平安志的派生数据，文件的原始快照字段会保留到御契备份。当前对 `rawSha256` 只校验字段格式，未验证平安志内部 MAC。缺失原始快照、来源不符、格式未知时，界面提示改用角色档案的 JSON 导出。

御契也支持分类合并档案中的已识别库存记录，保留各类别的来源并提示用户用同一次完整采集确认库存。导出明确将某类别标为未采集时，该类别可以省略。其他库存字段仍走原有的结构与实例 ID 校验。

角色档案按类别导出时可能省略 `equipPresets`。御契在增量导入时沿用省略的预设，收到明确的空列表时清空预设。当前库存与备份恢复使用同一份预设列表。

分类字段按程序里的条件读取。`0x1404e8761–0x1404e895c` 将游戏阵容预设 `lineupPresets` 与御魂预设分到御魂类别，将契灵、堆叠素材、碎片、碎片绑定、式神传记分到式神类别。`0x1404e897f–0x1404e8b07` 将资源余额和收藏分到物品，将结界卡、阴阳寮、任务记录分别归到相应类别。`0x1404e8b2c–0x1404e8e3f` 单独裁剪版本 1 的 `accountComparison`，按物品和结界卡的选项保留 `items` 和 `realm`，未选择两类时仍可提供 `appearance`。`0x140425e32–0x1404264e4` 是 MuMu 对同一批类别的禁用路径，会把部分字段写成空集合或 `null`，同时写入 `scope`。桌面构造函数 `0x140427d75` 只读取版本 1 的 `lineupPresets` 再写入桌面快照。

新导入会显示各字段的采集范围。账号页的「游戏阵容预设」读取版本 1 的 `teamPresets.teams` 和 `soulPlans.plans`，按实例引用显示可识别的式神和当前库存中可找到的御魂。队伍和御魂方案按各自的原生引用显示分组、成员及缺少的预设，并显示已识别结构的绑定条数。勾选增量合并时，明确未采集、省略或写成 `null` 的扩展字段可沿用旧记录，界面显示旧记录的时间。已采集的空集合可以清空旧数据。版本 1 账号概况的物品和结界分别判断，更新其中一项时可独立沿用另一项。备份保留原始预设，包括分组和方案绑定。绑定的两端语义及游戏阵容码互转仍待核对。

平安志桌面快照构造函数 `0x140427a68` 读取 `hunlings` 数组，再将该数组写入新快照。御契保留这部分原始库存。魂王复跑使用客户端 `HunlingDataKey` 对应的 `uid`、`id`、`lv`、`star`、`shiny` 和 `marks` 字段。战斗用技能表按原版 `HunlingAttrCalc` 和 `get_battle_souls` 生成，实际库存的实例标识在复跑前换为临时标识。

同一构造函数在 `0x14042a2a9` 的字段组装路径写入式神 `equips`。客户端 `HeroData.initFromDict` 读取该列表，`HeroComp.initHeroData` 按实例 ID 在库存中取御魂。御契据此核对当前穿戴，检查引用存在、槽位唯一且每件御魂只有一个穿戴者。账号界面显示核对后的已穿戴、未穿戴件数。缺少完整库存或实例引用存在冲突时，显示待核对。原始 `equippedState` 随库存保留。两份本机库存分别确认 98 件和 227 件已穿戴御魂。涉及的 90 个式神实例均通过保留穿戴的面板计算。

已用四份本机版本 2 MuMu 缓存验证导入与备份恢复。桌面、雷电、蓝叠、分类合并和按类别省略的语义使用合成记录验收。三个旧版原生标记已接到经核对的 `souls` 分支，仍须通过现有账号、式神和御魂结构校验。直接 JSON 和原生来源的版本 2 包装均通过合成记录回归，旧版本实际产物仍待验收。角色档案的其他导出物和藏宝阁库存也待验收。

版本 1 游戏阵容预设的界面与备份用按程序字段编写的合成记录验收。本轮追加核对的两份本机 MuMu 原始快照均可导入和恢复，两份均未提供游戏阵容预设。

旧式御魂预设使用顶层 `equipPresets`。平安志 `0x1404e880b–0x1404e8817` 将该字段按御魂类别原样复制，随后才处理 `lineupPresets`。两份实际角色导出中，旧式预设均为 `[名称, 御魂实例引用列表]`，列表允许为空或少于六件，也存在同名预设。御契按导出顺序逐项保留，在账号页的「御魂预设」中显示每项对应的库存御魂、实际槽位和缺失引用。已有配装计算仍会核对六个不同槽位及已识别属性。无法识别的预设保留在原始快照与备份中。

用已核对的平安志程序分别执行了角色档案批量导出和单角色历史导出。两个角色的 JSON 含 120 套和 193 套旧式御魂预设，其中分别有 100 套和 187 套的六槽齐全且属性可识别。单角色历史导出与该角色的批量导出文件 SHA-256 相同。三份 JSON 均通过御契的实际文件导入入口、账号页显示和备份解析。阴阳寮成员统计另有使用 `.xls` 扩展名的 HTML 报表。按类别导出的实际文件、旧版历史档案和其他来源的实物验收仍待补充。
